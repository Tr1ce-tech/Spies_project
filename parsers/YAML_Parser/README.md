# SkyTeam YAML → Parquet

Самостоятельный потоковый парсер `SkyTeam-Exchange.yaml` для учебного проекта
Catch The Spies. Работает без кода основного проекта. Исходный YAML уже находится
в `Airlines/`; в ZIP поставки он повторно не включён.

## Что означает строка

Вложенность источника:

```yaml
'2017-01-01':
  AF1145:
    FF:
      FB 520518073: {CLASS: Y, FARE: YRSTFN}
    FROM: SVO
    STATUS: LANDED
    TO: CDG
```

Из источника получаются **две связанные таблицы**:

1. `result/flights.parquet`: одна строка на ключ рейса внутри даты. Это исходная
   запись с маршрутом, статусом и вложенными данными, а не подтверждённый перелёт.
2. `result/loyalty_entries.parquet`: одна строка на элемент `FF` внутри рейса.
   Несколько карт означают несколько исходных записей, а не несколько рейсов.
   Карта сама по себе не идентифицирует доказанного уникального человека.

Связь: `flights.flight_record_id` → `loyalty_entries.flight_record_id`.
Рейс без карт остаётся в первой таблице с `loyalty_entry_count=0`. Дубликаты
значений между разными датами/рейсами не удаляются. В этом YAML нет имён
пассажиров и номеров билетов: они не выдумываются и не подмешиваются из Excel.

## Файлы поставки

- `parse_yaml.py`: потоковый парсер и запись обеих таблиц.
- `verify_yaml.py`: независимая сверка исходного текста, полный проход Parquet
  с проверкой связей и выборочное чтение сохранённых YAML-фрагментов другим движком.
- `test_parser.py`: автоматические тесты.
- `requirements.txt`: две зависимости с фиксированными версиями.
- `result/*.parquet`: готовые таблицы.
- `result/manifest.json`: SHA-256, количество строк по датам, статусы, ограничения,
  версии библиотек, время и контрольные суммы обоих результатов.
- `result/verification.json`: результаты проверки всего массива и образцы источника.
- `result/schema.txt`: схема таблиц и типы.
- `VALIDATION.md`: понятная сводка фактического запуска.
- `logs/`: вывод тестов, пробного и полного запусков, замеры памяти.
- `checksums.json`: контрольные суммы содержимого ZIP.

## Запуск

Проверено на Python 3.13. Linux/WSL:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest -v test_parser
python parse_yaml.py /путь/к/SkyTeam-Exchange.yaml --output new_result
python verify_yaml.py /путь/к/SkyTeam-Exchange.yaml new_result
```

Windows: `py -3.13 -m venv .venv`, затем `.venv\Scripts\Activate.ps1` и те же
команды `python`. Путь с пробелами заключайте в кавычки.

Для пробной обработки добавьте `--max-flights 10000`. Такой результат всегда
помечается `limited_run: true`, `complete: false`. Полный запуск требует нового
выходного каталога. Готовые файлы не перезаписываются автоматически.

## Архитектура и память

1. SHA-256 рассчитывается чтением блоков по 1 МиБ.
2. `yaml.parse(..., Loader=yaml.CBaseLoader)` выдаёт поток событий из файлового
   объекта. Нет `read()` всего YAML, `safe_load()` полного файла или гигантского
   DataFrame. Восстанавливается только один подсловарь рейса.
3. Второй последовательный файловый дескриптор сохраняет точный исходный
   YAML-фрагмент этого рейса. Это отдельное последовательное чтение, не полная
   копия текста в памяти. Сохраняются номера строк начала/конца и дата-родитель.
4. По каждой таблице накапливается не более 2 048 строк или примерно 4 млн
   символов строковых значений, затем пакет пишется через `ParquetWriter` с ZSTD.
   Это ограничение буфера, а не жёсткая квота памяти всего процесса.
5. Глубина вложенности, число узлов, длина скаляра и суммарный текст одного рейса
   ограничены. Ограничения приведены в `LIMITS` и в манифесте.
6. Множества проверенных ключей хранят только даты и рейсы текущего дня; все
   карты хранятся только для текущего рейса. Итоги накапливаются по датам.
7. Запись идёт в `имя_результата.partial`. Итоговый каталог появляется только
   после завершения, обратной проверки количества строк и повторного SHA-256 входа.
   При ошибке остаётся `FAILED.json`; такой каталог не объявляется успешным.

Ошибки синтаксиса, повторные ключи даты/рейса/карты/атрибута, неподдерживаемые
теги, anchors/aliases и несоответствующие схеме структуры останавливают запуск
с ненулевым кодом. Скрипт не пропускает ошибочные куски и не заменяет значения
по принципу «последний ключ побеждает». Anchors/aliases не разворачиваются.

Доступные замеры RSS и их ограничения приведены в `VALIDATION.md`.
Показатель измерялся снаружи процесса; `psutil` для запуска парсера не нужен.

## Поля

Общие поля обеих таблиц:

| Поле | Смысл |
|---|---|
| `source_file`, `source_sha256` | Имя и SHA-256 исходного файла |
| `rule_version` | Версия правил |
| `date_raw`, `date` | Исходный ключ даты и проверенная дата `date32` |
| `source_date_line` | Номер строки ключа даты в исходнике, начиная с 1 |
| `flight_number_raw`, `flight_number` | Исходный и нормализованный номер рейса |
| `origin_raw`, `origin` | Исходный FROM и нормализованный код аэропорта |
| `destination_raw`, `destination` | Исходный TO и нормализованный код аэропорта |
| `status_raw`, `status` | Статус из источника; LANDED не проверяется по внешним данным |

Дополнительно в `flights.parquet`:

| Поле | Смысл |
|---|---|
| `flight_record_id` | SHA-256 от хэша источника, ключа даты и ключа рейса |
| `source_start_line`, `source_end_line` | Границы записи рейса в исходном файле |
| `date_key_style`, `flight_key_style` | Стиль кавычек исходных YAML-ключей |
| `loyalty_entry_count` | Число элементов FF |
| `raw_flight_yaml` | Исходный фрагмент YAML, включая ключ рейса и все поля |
| `raw_flight_json` | Разобранный подсловарь, включая FF и неизвестные дополнительные поля |
| `scalar_styles_json` | Стили кавычек/явные поддержанные теги нестандартно оформленных скаляров |
| `field_status_json` | Статусы нормализации общих полей |

Дополнительно в `loyalty_entries.parquet`:

| Поле | Смысл |
|---|---|
| `entry_id` | SHA-256 от ID исходной записи рейса и исходного ключа карты |
| `flight_record_id` | Ссылка на первую таблицу |
| `loyalty_key_raw` | Полный исходный ключ, например `SU 000001` |
| `loyalty_program`, `loyalty_number` | Префикс программы и **строковый** номер карты |
| `source_line`, `source_column` | Строка и колонка ключа карты, начиная с 1 |
| `loyalty_key_style` | Стиль исходного ключа |
| `class_raw`, `travel_class` | CLASS как исходное и очищенное значение |
| `fare_raw`, `fare` | FARE как исходное и очищенное значение |
| `raw_entry_json` | Все исходные атрибуты элемента FF |
| `field_status_json` | Статусы карты, класса и тарифа |

## Очистка и ограничения

- Скалярные значения извлекаются как текст, без неявного преобразования YAML
  в int/bool/date. Например, `000001`, `ON` и `001ABC` не теряют исходное написание.
  Нестандартные кавычки отражаются в метаданных, а исходный YAML сохранён целиком
  на уровне рейса. Отсутствующее поле, пустой скаляр и маркер пропуска различимы.
- Только ISO-даты `YYYY-MM-DD` проверяются по календарю и преобразуются в
  `date32`. Порядок дня/месяца в неоднозначной строке не угадывается.
- Идентификаторы — строки, начальные нули сохраняются. Карта — пара префикса
  программы и номера, а не один номер без программы.
- Нормализация текста: NFC и удаление внешних пробелов. Коды аэропортов и рейсов
  дополнительно приводятся к верхнему регистру и проверяются по синтаксису.
- Маркеры N/A, NA, NULL, NONE, NAN, «-», «~» дают пустое нормализованное значение;
  исходная строка остаётся. Нераспознанные поля не теряются в raw JSON/YAML.
- Синтаксически допустимый код не считается исторически проверенным аэропортом.
  Исходный `rea` превращается только в `REA`; маршрут по нему не исправляется.
- Время, часовые пояса, names, ticket numbers и реальный оператор здесь не
  восстанавливаются: соответствующих оснований в источнике нет.

## Как проверена полнота

Независимый построчный сканер проверяет **каждую строку** по фактически
наблюдаемой структуре этого файла и останавливается на незнакомом синтаксисе.
Он независимо считает даты, рейсы, карты, CLASS/FARE и маршруты, затем считает
упорядоченные SHA-256 содержимого рейсов и элементов FF. Эти суммы сравниваются
с полным проходом Parquet. В этот расчёт входят все записи, а не только образцы.

Все строки обеих таблиц читаются пакетами и соединяются последовательно:
проверяются уникальность ключей, внешние ссылки, общие поля, число карт,
сырые поля, ID, даты, происхождение и сохранность номеров. Несколько исходных
YAML-фрагментов дополнительно разбираются независимым чисто Python-движком
`yaml.BaseLoader` и сверяются с сохранёнными структурами.

Сам парсер поддерживает больше YAML-конструкций, чем независимый сканер;
сканер намеренно привязан к данному формату и при изменении источника может
потребовать отдельного обновления. Успех этих проверок подтверждает извлечение
данных, а не истинность сведений о поездках.

## Пример чтения

```python
import pyarrow.parquet as pq

flights = pq.ParquetFile("result/flights.parquet")
print("Исходные записи рейсов:", flights.metadata.num_rows)

# Обрабатывайте пакетами; не загружайте все подробные поля без необходимости.
for batch in pq.ParquetFile("result/loyalty_entries.parquet").iter_batches(
    batch_size=10_000,
    columns=[
        "date",
        "flight_number",
        "origin",
        "destination",
        "loyalty_program",
        "loyalty_number",
        "travel_class",
        "fare",
    ],
):
    print(batch.slice(0, 3).to_pylist())
    break
```
