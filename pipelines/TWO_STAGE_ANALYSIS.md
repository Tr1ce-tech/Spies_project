# Общий Parquet и отбор профилей

Две точки запуска работают последовательно. Первая читает результаты парсеров,
вторая — только созданный общий файл. Персональные результаты хранятся локально;
ни один скрипт не обращается к внешним сервисам и не работает с Git.

Из корня проекта, в текущем виртуальном окружении:

```bash
.venv/bin/python -m pip install -r pipelines/profile_patterns_requirements.txt

.venv/bin/python -m pipelines.build_common_parquet \
  --input-dir parsers \
  --output proceed_data/common_v1/travel.parquet

.venv/bin/python -m pipelines.filter_profiles \
  --input proceed_data/common_v1/travel.parquet \
  --output proceed_data/query_v1/profiles.parquet \
  --json-output proceed_data/query_v1/profiles.json \
  --criteria high_frequency,many_routes \
  --set high_frequency.minimum=30 \
  --set many_routes.minimum=25 \
  --match any
```

## Первый скрипт: build_common_parquet

`--input-dir` — любой общий каталог с файлами Parquet. Вложенные папки тоже
просматриваются. Имена файлов не важны: таблицы определяются по схеме полей.
Текущая версия поддерживает известные схемы шести пассажирских парсеров проекта:
CSV, TAB, Excel, JSON (profiles/cards/flights), XML (users/cards/activities),
YAML (loyalty_entries). Нужны все эти таблицы; отдельная таблица рейсов YAML
уже продублирована в loyalty_entries и для пассажирского слоя не требуется.
PDF и вспомогательные таблицы не входят в пассажирский массив.

В нашем проекте можно передать `parsers`, не копируя результаты в одну плоскую
папку. Если таблицы уже собраны в другой папке, передать её путь. Выход должен
находиться за пределами входной папки. Исходные таблицы не изменяются.

Папки legacy/legacy_pdf и служебные директории исключаются. Полностью одинаковые
дубликаты файлов учитываются один раз. Перекрывающиеся ID в неидентичных выгрузках
вызывают ошибку; объединять старые и новые версии экспорта молча нельзя.
Числовые типы документов, билетов и карт отклоняются: начальные нули не угадываются.

Общий файл имеет версию `travel-common.v1` и плоскую структуру:

- одна строка `record_kind=observation` на первичное наблюдение;
- одна строка `record_kind=entity_only` для исходной сущности без наблюдений;
- source/entity_id/entity_kind, имена из источника, документы и наборы вариантов
  даты рождения; поля с `_raw` — входные значения соответствующего слоя, не
  обязательно точные байты исходного CSV/XML. Точные оригиналы доступны через
  source_record_id и SHA-256 в результатах парсеров;
- исходные и общие дата, рейс, аэропорты, билет, локальное время, PNR;
- ID кандидата компонента, ID предварительной группы и статус связи отдельно;
- candidate_document_count и component_reasons_json описывают компонент
  кандидатов, а не документы, достоверно принадлежащие конкретному профилю;
- исходные record_id, SHA-256, локаторы, версии парсера и правил нормализации.

identifier_assertions_json хранит все утверждения о документах/картах один раз
на сущность: только в первой её строке. У остальных строк поле null. Это
нормализация хранения, не отсутствие идентификаторов. Строковые значения и
начальные нули сохранены. Количество утверждений сверяется перед экспортом.

В Parquet metadata включены `travel.schema_version` и `travel.manifest`:
состав входов, их размеры/число строк/SHA-256, исключённые файлы, версии кода и
контрольные количества. Общий файл переносим: второй скрипт не открывает пути
из этого журнала и не требует исходного каталога или прежних proceed_data.

Сопоставление использует точный документ и программу вместе с номером карты.
Противоречия проверяются на уровне целого компонента; удержанные компоненты не
становятся принятыми группами. Несколько документов могут быть допустимыми,
но автоматически подтверждать такую связь нельзя. Билет/дата/рейс не используются
здесь для автоматического присвоения паспорта или объединения людей.

## Второй скрипт: filter_profiles

```bash
.venv/bin/python -m pipelines.filter_profiles --list-criteria
```

Вывод JSON содержит стабильные ID критериев, русские названия, категории,
описания и типы/границы/значения по умолчанию параметров — его может читать UI.

| ID | Критерий | Основные параметры |
|---|---|---|
| high_frequency | Много разных блоков дата/рейс | minimum или quantile |
| many_routes | Много согласованных направлений | minimum или quantile |
| repeated_route | Повторение главного направления | min_count, min_share |
| date_concentration | Концентрация за 7 календарных дней | min_count, min_share или quantile |
| rare_routes | Редкость направлений в когорте | min_routes, minimum или quantile |
| document_discrepancy | Участие в неразрешённом компоненте с разными документами | minimum |
| route_conflict | Разные маршруты внутри блока дата/рейс | minimum |
| busy_day | Несколько разных рейсов в одну календарную дату | minimum |

`--set КРИТЕРИЙ.ПАРАМЕТР=JSON_ЗНАЧЕНИЕ` задаёт пороги выбранных критериев.
Например, `--set repeated_route.min_share=0.5`. Неизвестные критерии, параметры,
NaN, булевы числа и значения вне границ отклоняются. Можно использовать JSON:

```bash
.venv/bin/python -m pipelines.filter_profiles \
  --input proceed_data/common_v1/travel.parquet \
  --output proceed_data/query_config/profiles.parquet \
  --config pipelines/travel_analysis/example_query.json
```

Конфигурация и отдельные опции выбора не смешиваются. В JSON — `criteria`
(объект выбранных правил и параметров), `match` (`any`/`all`) и `unit_kinds`.
Без явного выбора используются первые пять правил и локальные профили.

Если minimum/min_share не заданы, используются строгие превышения процентиля
когорты (по умолчанию 0.99). Для сравнения нужны 5 блоков, 3 даты, 80% покрытия
согласованными маршрутами и минимум 200 единиц в когорте. Абсолютные пороги не
требуют 200 единиц: они сравнивают непосредственно измеряемый показатель.
Для many_routes/repeated_route покрытие маршрутами остаётся не ниже 80%.
Редкость всегда требует достаточно большой сопоставимой когорты, потому что
является относительным показателем. Фиксированные минимумы числа повторов,
блоков и направлений описаны в JSON критериев. Настройка численного порога
влияет на размер результата и не является оценкой precision/recall.

Результат — Parquet выбранных единиц; опционально JSON для UI. Есть имена по
источникам (names_json), показатели, matched_criteria, criteria_count и
reasons_json с наблюдаемым значением, оператором, порогом, знаменателями и
объяснением. В metadata `travel.selection` — конфигурация, количества,
SHA-256 общего файла и версия расчёта. Даже пустой результат — корректный
Parquet со схемой. Существующие файлы не перезаписываются.

В JSON поле profiles содержит уже разобранные массивы names, reasons и
document_context_components. В summary отдельно указаны все рассматриваемые
единицы и единицы, пригодные для сравнения с когортой. Отсутствие профиля в
результате не означает, что он проверен и признан обычным.

`--unit-kinds source_profile` — собственные профили JSON/XML.
`--unit-kinds preliminary_group` — предварительно согласованные группы.
Можно передать оба через запятую, но они пересекаются по наблюдениям и их нельзя
складывать как число людей. Несвязанные CSV/TAB/Excel-записи и YAML-счета остаются
в общем файле; они не объявляются полноценными пассажирскими профилями.

Документный критерий выделяет контекст проблемы сопоставления: документы не
присваиваются профилю. Route conflict может означать многоучастковый рейс;
busy day не доказывает невозможное перемещение. Даты и местное время не
переводятся в UTC. Доказательств реального перелёта и целевых меток нет.

## Подключение будущего UI

```python
from pipelines.filter_profiles import load_features
from pipelines.travel_analysis.criteria import CRITERIA, select_profiles

features, manifest = load_features("proceed_data/common_v1/travel.parquet")
selected, reasons, normalized_config = select_profiles(features, {
    "criteria": {"high_frequency": {"minimum": 30}, "busy_day": {"minimum": 3}},
    "match": "any",
    "unit_kinds": ["source_profile"],
})
```

UI загружает features один раз на версию общего файла, показывает поля из
CRITERIA и повторно вызывает select_profiles после смены настроек. Тяжёлое
извлечение из общего файла не нужно повторять при каждом переключении галочки.
Расчёт критериев не обучает Isolation Forest и не использует его score.
Он возвращает «профили для проверки», без вероятности преступной причастности.

## Проверки

```bash
.venv/bin/python -m unittest pipelines.test_two_stage_analysis -v
```

Интеграционный тест создаёт все схемы парсеров с синтетическими записями,
собирает общий файл, удаляет входной каталог и выполняет второй этап. Проверяются
профиль без поездок, пустой результат, защита от перезаписи, повторных выгрузок,
числовых идентификаторов, неправильных параметров и скрытой зависимости от
исходников. Это технические проверки, не эмпирическая точность сопоставления.
